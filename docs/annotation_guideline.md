# 岗位信息人工标注规范

版本：v1.0  
适用数据：产品经理、大模型评测、数据分析实习岗位  
用途：建立可复核的人工标准答案，用于评测大模型对招聘信息的结构化提取能力。

## 1. 标注对象与输出格式

- 每条招聘信息对应 `gold_dataset.jsonl` 中的一行 JSON。
- `input` 保存模型可读取的原始招聘信息，不改写原文。
- `gold` 保存人工确认后的标准字段。
- `evidence` 保存支持标准字段的原文证据。证据必须能够在 `input` 或页面顶部结构化信息中找到。
- 数组没有内容时填写 `[]`，单值字段没有信息时填写 `null`。不得用常识补全。

## 2. 字段定义

### 基础字段

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `schema_version` | 字符串 | 当前为 `1.0`。 |
| `job_id` | 字符串 | 与原始岗位表一致的唯一编号。 |
| `source` | 对象 | 来源平台、URL 和采集日期。 |
| `input` | 对象 | 原始职位名称、公司、城市、职责、要求、加分项和页面顶部结构化信息。 |

`input.page_metadata` 保存页面顶部直接展示的 `location`、`salary_yuan_per_day`、`education`、`work_days_per_week` 和 `internship_months`。这些字段属于模型可见原始输入，不是从 `gold` 动态读取的答案；推理时必须与正文一起传入。

### `gold` 标准答案字段

| 字段 | 类型 | 标注规则 |
| --- | --- | --- |
| `job_category` | 字符串 | 取 `产品经理`、`大模型评测` 或 `数据分析`。 |
| `employment_type` | 字符串或 `null` | 原文明确为实习时标为 `实习`。 |
| `role_focus` | 字符串数组 | 用 2～5 个短语概括岗位主要方向，不添加原文未体现的方向。 |
| `location` | 字符串或 `null` | 城市级地点。 |
| `salary_yuan_per_day` | 对象或 `null` | 日薪上下限，分别写入 `min` 和 `max`。 |
| `education_min` | 字符串或 `null` | 最低学历，如 `本科`、`硕士`。`本科及以上`规范化为`本科`。 |
| `student_status` | 字符串或 `null` | 如 `在校生`。仅在原文明示时填写。 |
| `graduation_year` | 对象或 `null` | “2028届及以后”标为 `{"min": 2028}`；仅限“2027届”标为 `{"exact": 2027}`。没有毕业年份要求时填 `null`。 |
| `work_days_per_week` | 整数或 `null` | 每周最低到岗天数。来源冲突时采用页面顶部结构化值，并在 `ambiguities` 保留冲突。 |
| `internship_months` | 整数或 `null` | 最短实习月数。优先条件不得写成最低要求。 |
| `core_tasks` | 字符串数组 | 将岗位职责归纳为可比较的任务短语。 |
| `required_hard_skills` | 字符串数组 | 任职要求明确要求的专业能力、方法或知识。不能仅因职责涉及某项工作就推断候选人必须已掌握。 |
| `required_tools` | 字符串数组 | 原文明确要求熟练、会使用或掌握的工具。 |
| `required_soft_skills` | 字符串数组 | 明确要求的沟通、逻辑、责任心等通用能力。 |
| `required_domain_conditions` | 字符串数组 | 明确要求的行业兴趣、用户身份、年级或其他背景条件。 |
| `preferred_hard_skills` | 字符串数组 | 由“优先”“加分项”等措辞限定的专业能力或工具。 |
| `preferred_experience` | 字符串数组 | 明确列为优先的实习、行业或项目经历。 |
| `preferred_background` | 字符串数组 | 优先专业、背景或更长实习时间等。 |
| `preferred_soft_skills` | 字符串数组 | 明确写在加分项中的责任心、沟通、探索意愿等通用能力。 |
| `ambiguities` | 对象数组 | 截断、来源冲突、岗位类别与实际职责不一致等问题。 |

### `evidence` 证据字段

`evidence` 的键应与重要标准字段对应，值为原文证据数组。例如：

```json
{
  "required_tools": ["熟练使用Office；有Axure、墨刀或Figma等工具使用经验者优先。"],
  "work_days_per_week": ["页面顶部：5天/周"]
}
```

证据应保留原意和限定词。“优先”“至少”“以上”“不限”等词不能删除。

## 3. 必备项与加分项的判断

1. 出现在“任职要求”中且没有“优先”“加分”等限定词的内容，标为必备项。
2. 出现“优先”“加分项”“有……经验者优先”的内容，标为加分项。
3. 岗位职责只标入 `core_tasks`。除非职责同时明确要求候选人具备某项能力，否则不自动转成必备技能。
4. 同一句同时包含必备和优先内容时必须拆分。例如“熟练使用Office；有Figma经验者优先”应分别标为 `required_tools: ["Office"]` 与 `preferred_hard_skills: ["Figma"]`。
5. “能实习6个月者优先”不能把最低实习期限改为6个月，应保留最低期限并将6个月写入 `preferred_background`。

## 4. 规范化规则

- 工具名称保留官方写法：`SQL`、`Office`、`Figma`、`Cursor`、`Claude Code`。
- 同义表达统一为便于统计的短语。例如“用户真实痛点调研”可规范化为“用户研究”。
- 不扩大概念。例如原文只写“数据分析能力”，不能标为“Python”“统计建模”。
- 不根据公司或岗位名称推断技能。例如“大模型评测”岗位不能自动添加“Python”。
- 软技能使用简短名词短语，如“逻辑分析”“沟通能力”“责任心”。
- `core_tasks` 应描述工作内容，不评价难度或重要性。

## 5. 冲突和不完整信息

- 页面顶部和正文发生冲突时，两处证据都要记录。
- 为保持原始表格的一致性，`work_days_per_week` 和 `internship_months` 暂以页面顶部结构化信息为标准值。
- 在 `ambiguities` 中填写：冲突字段、采用值、其他值和原因。
- 页面标题被截断时，不猜测完整标题，在 `ambiguities` 中标记 `title_truncated`。
- 岗位名称与职责方向不一致时保留原始分类，并标记 `role_mismatch`，留待后续聚类分析。

## 6. 标注流程

1. 阅读页面顶部结构化信息、岗位职责、任职要求、加分项和备注。
2. 先原样填写 `input`。
3. 标注基础条件：地点、薪资、学历、到岗天数、实习期限。
4. 提炼 `core_tasks`，再分别提取必备与优先条件。
5. 为关键字段补充证据。
6. 检查是否存在冲突、截断或推断，并写入 `ambiguities`。
7. 使用 JSON 解析器验证每行格式。

## 7. 质量检查清单

- [ ] 每条记录只有一行，且是合法 JSON。
- [ ] `job_id` 与原始岗位表一致且不重复。
- [ ] 每个必备项都能在原文中找到直接证据。
- [ ] 必备项和优先项没有混淆。
- [ ] 未提及内容使用 `null` 或 `[]`，没有凭常识补充。
- [ ] 数值冲突、标题截断等问题已写入 `ambiguities`。
- [ ] 工具名称和同义词使用统一写法。

## 8. 标注范围

首批选择三个代表性岗位验证字段：

1. `PM_001`：产品经理实习生，心野引行。
2. `LLMEVAL_001`：大模型数据策略产品实习生，至知科技。
3. `DA_002`：数据分析实习生，丞策信息科技。

字段验证通过后，其余六条岗位继续按同一规范标注。当前数据集共包含9条人工标准答案，覆盖产品经理、大模型评测和数据分析各3条。

## 9. 开发集与验证集隔离

- `data/annotated/gold_dataset.jsonl` 是开发集，可用于设计规则、提示词和归一化别名。
- `data/validation/validation_dataset.jsonl` 是冻结验证集，只用于检验泛化能力。
- 在验证集完成首轮盲测前，不得根据其中的岗位文本、标准答案或错误案例修改提取规则、提示词和别名表。
- 若首轮盲测后决定继续调参，应把这批数据改记为开发集，并另行收集未见过的测试集，不能继续把它报告为独立验证结果。
